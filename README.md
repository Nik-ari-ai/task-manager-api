# Task Manager API

REST API для управления задачами и их статусами.

Стек: PHP 8.3, Symfony 6.4 LTS, PostgreSQL 16, Docker Compose.

## Как запустить

Требуется установленный Docker с Docker Compose.

```bash
git clone <URL репозитория>
cd task-manager
docker compose up -d --build
```

При старте контейнер `php`:

1. устанавливает зависимости через Composer, если каталог `vendor` отсутствует;
2. ждёт готовности PostgreSQL (healthcheck базы + ожидание в entrypoint);
3. применяет миграции (`doctrine:migrations:migrate`), которые создают таблицы и
   заливают три системных статуса: `new`, `in_progress`, `done`.

Если в репозитории есть `composer.lock`, Composer устанавливает точные версии из
него. Чтобы сгенерировать lock-файл локально (нужен один раз, затем он коммитится):

```bash
docker compose run --rm php composer update --lock
```

После запуска API доступно по адресу:

```
http://localhost:8080
```

Базовый префикс всех ресурсов — `/api`. Например, список задач:

```
http://localhost:8080/api/tasks
```

Документация OpenAPI (Swagger UI):

```
http://localhost:8080/api/doc
```

### Проверка статуса

```bash
docker compose ps
docker compose logs php
```

### Остановить

```bash
docker compose down
```

Удалить вместе с данными базы:

```bash
docker compose down -v
```

## Эндпоинты

### Задачи

| Метод  | Маршрут                      | Описание                     |
|--------|------------------------------|------------------------------|
| POST   | `/api/tasks`                 | Создать задачу               |
| GET    | `/api/tasks`                 | Список задач                 |
| GET    | `/api/tasks?status=done`     | Список задач с фильтром      |
| GET    | `/api/tasks/{id}`            | Получить задачу              |
| PATCH  | `/api/tasks/{id}/status`     | Изменить статус задачи       |
| DELETE | `/api/tasks/{id}`            | Удалить задачу               |

### Статусы

| Метод  | Маршрут                | Описание            |
|--------|------------------------|---------------------|
| GET    | `/api/statuses`        | Список статусов     |
| GET    | `/api/statuses/{id}`   | Получить статус     |
| POST   | `/api/statuses`        | Добавить статус     |
| DELETE | `/api/statuses/{id}`   | Удалить статус      |

## Коды ответов

| Ситуация                                                | Код |
|---------------------------------------------------------|-----|
| Создание задачи или статуса                             | 201 |
| Получение, список, изменение статуса                    | 200 |
| Удаление                                                | 204 |
| Некорректный JSON в теле запроса                         | 400 |
| Тело запроса не является JSON-объектом                   | 400 |
| Ошибки валидации входных данных                          | 422 |
| Неизвестный статус в теле PATCH                          | 422 |
| Несуществующая задача или статус-ресурс                  | 404 |
| Неизвестный статус в фильтре `GET /api/tasks?status=`    | 404 |
| Дублирование `name` статуса                              | 409 |
| Удаление статуса, к которому привязаны задачи            | 409 |
| Удаление системного статуса                              | 409 |

Формат ошибки единый:

```json
{
    "error": "The status is in use and cannot be deleted.",
    "details": {
        "status": "done",
        "tasks_count": 3
    }
}
```

## Архитектурные решения и компромиссы

1. **Связь Task и Status — `ManyToOne`.** Status вынесен в отдельную сущность со
   своим CRUD, как требует задание. Задача всегда ссылается на один статус через
   внешний ключ `task.status_id`. На столбец `status.name` наложен уникальный
   индекс, потому что по нему идёт фильтрация и по нему же задаётся статус в PATCH.

2. **Удаление статуса защищено на двух уровнях.** В сервисе проверяется, что
   статус не системный и что на него не ссылаются задачи, — иначе возвращается
   `409` с понятным сообщением и количеством задач. На уровне базы внешний ключ
   объявлен с `ON DELETE RESTRICT`. Предварительный `COUNT` даёт дружелюбный
   ответ, а внешний ключ закрывает гонку между проверкой и удалением: если задача
   будет привязана между этими двумя шагами, база отклонит удаление. В этом случае
   `ForeignKeyConstraintViolationException` сразу превращается в `409` без
   повторного обращения к EntityManager (после ошибки `flush()` менеджер
   закрывается, поэтому повторные запросы через него недопустимы). Целостность
   гарантирует база, а не только проверка.

3. **Системные статусы нельзя удалять.** Три статуса `new`, `in_progress`, `done`
   помечены флагом `is_system = true` и заливаются data-миграцией. Статус `new`
   назначается новой задаче по умолчанию, поэтому его удаление сломало бы
   создание задач. Запрет на удаление системных статусов закрывает этот случай.

4. **Слои: Controller → Service → Repository.** Контроллеры тонкие: разбирают
   запрос, вызывают сервис, возвращают HTTP-код. Бизнес-логика (создание задачи,
   смена статуса, проверки перед удалением) живёт в сервисах. Доступ к данным —
   в репозиториях. Контроллеры не содержат сырого SQL.

5. **Разбор и валидация входных данных вынесены в `JsonRequestDecoder`.**
   Он разбирает тело через `json_decode(..., JSON_THROW_ON_ERROR)` (некорректный
   JSON → `400`), проверяет, что корень — объект, а не массив или скаляр,
   отображает данные в DTO и прогоняет через валидатор (ошибки полей → `422`).
   Благодаря этому контроллер остаётся тонким, а границы `400`/`422` — явными.

6. **Обработка ошибок централизована в `ExceptionListener`.** Доменные исключения
   реализуют интерфейс `ApiException` и сами сообщают свой HTTP-код и детали.
   Listener превращает их в единообразный JSON-ответ, поэтому контроллеры и
   сервисы не занимаются формированием ошибок.

7. **Метка времени `updated_at` обновляется явно в сервисе.** При смене статуса
   меняется только связь, и Doctrine в `PreUpdate` не всегда включает такое поле
   в change set. Поэтому `updated_at` обновляется явным вызовом `touch()` перед
   `flush()`, а `created_at`/`updated_at` при создании проставляются в
   `PrePersist`. Это поведение покрыто функциональным тестом.

## Что сознательно упрощено

- DTO отображаются в объект простым перебором свойств, без тяжёлого компонента
  сериализации, — для трёх небольших DTO этого достаточно.
- Поля DTO типизированы как `mixed` и проверяются через `Assert\Type`, чтобы
  некорректный тип приходил как ошибка валидации `422`, а не как `TypeError`.
- Не вводились интерфейсы и абстракции сверх необходимого: сервисы внедряются
  напрямую.

## Примеры запросов (curl)

Создать задачу:

```bash
curl -i -X POST http://localhost:8080/api/tasks \
    -H "Content-Type: application/json" \
    -d '{"title": "Подготовить отчет", "description": "Отчет по продажам за май"}'
```

Создать задачу без описания:

```bash
curl -i -X POST http://localhost:8080/api/tasks \
    -H "Content-Type: application/json" \
    -d '{"title": "Задача без описания"}'
```

Список задач:

```bash
curl -i http://localhost:8080/api/tasks
```

Список задач с фильтром по статусу:

```bash
curl -i "http://localhost:8080/api/tasks?status=done"
```

Получить задачу:

```bash
curl -i http://localhost:8080/api/tasks/1
```

Изменить статус задачи:

```bash
curl -i -X PATCH http://localhost:8080/api/tasks/1/status \
    -H "Content-Type: application/json" \
    -d '{"status": "done"}'
```

Удалить задачу:

```bash
curl -i -X DELETE http://localhost:8080/api/tasks/1
```

Список статусов:

```bash
curl -i http://localhost:8080/api/statuses
```

Получить статус:

```bash
curl -i http://localhost:8080/api/statuses/1
```

Добавить статус:

```bash
curl -i -X POST http://localhost:8080/api/statuses \
    -H "Content-Type: application/json" \
    -d '{"name": "code_review", "title": "Ревью кода"}'
```

Удалить статус:

```bash
curl -i -X DELETE http://localhost:8080/api/statuses/4
```

## Тесты

Функциональные тесты (PHPUnit) запускаются внутри контейнера. Для них нужна
отдельная база `task_manager_test`:

```bash
docker compose exec php php bin/console doctrine:database:create --env=test --if-not-exists
docker compose exec php php bin/phpunit
```

Функциональные тесты контроллеров пересоздают схему перед каждым запуском через
`SchemaTool` и загружают системные статусы. Отдельный тест миграций
(`tests/Migrations/MigrationsTest.php`) работает иначе: он сбрасывает базу и
прогоняет реальные миграции `doctrine:migrations:migrate`, а затем проверяет, что
схема и системные статусы созданы. Так ошибки в SQL миграций ловятся тестом, а не
только в рантайме.

Покрытие:

- создание задачи со статусом по умолчанию `new`;
- сохранение `null` в описании при отсутствии поля;
- валидация входных данных (`422`), в том числе некорректный тип поля;
- некорректный JSON (`400`) в POST и PATCH;
- корень запроса не является объектом: массив, пустой массив `[]`, строка (`400`);
- пустое тело запроса (`400`);
- список задач и фильтр по существующему статусу;
- фильтр по неизвестному статусу (`404`);
- смена статуса с проверкой обновления `updated_at`;
- неизвестный статус в PATCH (`422`);
- удаление задачи (`204`) и удаление несуществующей задачи (`404`);
- создание статуса с невалидным `name` (`422`);
- дубликат имени статуса (`409`);
- удаление используемого статуса (`409`);
- удаление системного статуса (`409`);
- удаление несуществующего статуса (`404`);
- прогон реальных миграций на чистой базе.
